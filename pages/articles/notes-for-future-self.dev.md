# 未来の自分が続きを書ける開発メモ

::: info サンプル記事
この記事の作業内容やエピソードは架空です。長い段落、リスト、表、折りたたみなどの表示確認に使えます。
:::

昨日まで何をしていたのか、思ったより簡単に忘れてしまう。コードを開くと変更した場所はわかるのに、なぜそこを変更したのかがうまく思い出せない。ターミナルには実行履歴が残っていても、どの結果を見て次の操作に進んだのかまでは残っていない。

作業中は、頭の中でいくつもの情報がつながっている。画面で見た違和感、直前に読んだ実装、試して失敗した案。そのつながりがあるうちは、短いメモでも意味が通る。ところが、数日後に読み返すと「ここを直す」の「ここ」がどこなのかわからなくなる。

未来の自分に引き継ぐつもりで記録を書いたら、何を残すだろう。今回は、架空の表示不具合を調べる作業を例に、開発メモの形を考えてみる。

[[toc]]

## 最初に、何が起きたかを書く

不具合を見つけると、すぐに原因を予想したくなる。「キャッシュが古いのかもしれない」「文字数の計算がおかしいのかもしれない」。予想は調べる入口として役立つが、最初の記録には、見えた現象も残しておきたい。

たとえば「記事一覧がおかしい」だけでは、後から同じ状態を作るのが難しい。「長い記事を追加した後も、一覧の読了時間が一分と表示された」なら、確認する対象が少し絞れる。

さらに、どのページで、どんな操作をして、何を期待したのかを書き足す。長い説明にする必要はない。次のような短い記録でも、手がかりになる。

```text
対象: ローカルの記事一覧
操作: 長文の記事を追加してページを再読み込み
期待: 本文の長さに応じた読了時間になる
実際: 追加前と同じ一分の表示だった
```

この時点で原因は決めない。まず、あとからもう一度観察できる形にする。

## 観察と予想を混ぜない

調査が進むと、わかったことと、まだ確かめていないことが同じメモに増えていく。ここが混ざると、最初に思いついただけの予想を、確認済みの事実として扱ってしまいそうになる。

記録には、必要な範囲で状態を添える。「画面で確認した」「コードを読んでそう考えた」「まだ試していない」。言葉を少し足すだけで、情報の重さが伝わる。

| 種類   | 記録の例                                   | 次にできること         |
| ------ | ------------------------------------------ | ---------------------- |
| 観察   | 長文の記事でも一分と表示された             | 同じ操作で再現する     |
| 確認   | 計算に渡った本文は空文字列だった           | 本文の取得元を調べる   |
| 予想   | 記事のパスと取得時のキーが違うかもしれない | 両方の値を比較する     |
| 未確認 | ビルド後にも同じ現象が起きるか             | 本番向け出力を確かめる |

この表は、記事の題材として作った調査例だ。実際の作業では毎回表にしなくてもよい。ただ、「見たこと」と「考えたこと」の境目を言葉にすると、別の可能性を考え直しやすくなる。

## 実行したことより、結果を残す

コマンドの履歴だけを残しても、そのとき何が起きたのかは伝わりにくい。同じコマンドでも、入力したファイルや実行した場所によって、結果が変わることがある。

そのため、作業メモには操作と結果を一組で残す。「ビルドを実行した」の次に、「最後まで完了した」「どの段階で止まった」「警告が残った」と続ける。失敗したときは、判断に使ったエラーの文言も残しておきたい。

結果が長い場合は、全文を本文に貼ると流れが見えにくくなる。最初に要点を書き、必要な詳細は別に置くと、読み返すときに助かる。

::: details 調査メモの記入例
これは架空の記録です。

- 試したこと：記事のパスと本文取得時のキーを比較した。
- 結果：片方だけに拡張子が残っていた。
- 次の確認：他の記事でも同じ規則になっているかを見る。
- 保留：修正後の狭い画面での表示確認。

原因の候補が絞れた段階なので、この時点では「修正完了」と書かない。
:::

## 試さなかった案にも短い理由を付ける

一度考えて見送った案は、時間がたつとまた魅力的に見える。なぜ採用しなかったのかを忘れると、同じ調査を繰り返してしまう。

すべての案を詳細に比較する必要はない。「記事ごとに時間を手入力する案は、本文の変更時に更新を忘れそうなので見送った」。そのくらいの一文があれば、当時の判断をたどれる。

ただし、見送った理由と、絶対に使えない理由は違う。いまは記事数が少ないから不要だった仕組みも、後で必要になるかもしれない。前提を一緒に書いておくと、状況が変わったときに判断し直せる。

> 何を選んだかと、そのとき何を前提にしていたかを、一緒に残す。

これなら、過去の決定に縛られすぎず、同じ迷いを最初からやり直す負担も減らせる。

## 作業の最後に、再開の入口を用意する

作業を終えるころは、たいてい少し疲れている。きれいな報告を書こうとすると、メモを書くこと自体が後回しになる。そのため、終わりに残す情報は少なくしたい。

まず、いまどこまで進んだか。次に、まだ確認していないこと。最後に、再開したら最初に何をするか。この三つだけなら、短い時間でも書けそうだ。

```text
ここまで: 本文取得時のパスを揃え、一覧の表示が変わることを確認
未確認: 別の記事と、本番向けビルドの結果
次の一手: 長さの違う二つの記事を開き、一覧の読了時間と見比べる
```

「明日続きをやる」よりも、最初の一手がわかる文章にする。再開した直後は、作業中の自分ほど事情を覚えていない。その状態でも迷わず始められることを目標にする。

## 書きすぎたメモを少しだけ整える

調べている最中のメモは、順番が前後していてもよいと思う。思いついたことをすぐ残せるほうが役に立つ。ただ、ひと区切りついたら、後から必要になる情報を上に集めておきたい。

先頭に置くのは、結論と現在の状態。その次に、結論を支える観察。細かい試行錯誤は下に残す。これなら、急いでいるときには最初の数行だけ読めるし、理由が必要なときには続きを追える。

見出しを増やしすぎると、今度は書く場所を選ぶことに時間がかかる。小さな作業なら「わかったこと」「残っていること」の二つだけでも十分だった。形式を揃える目的は、記録を豪華にすることではなく、次に探す場所をわかりやすくすることにある。

## メモを残す相手は、記憶の薄れた自分

開発メモは、すべてを説明する教科書である必要はない。けれど、作業中の頭の中をそのまま写しただけでは、数日後の自分には読めないことがある。

現象を一つ具体的に書く。予想には予想だと添える。確認結果と未確認の範囲を分ける。次にやる操作を一つだけ残す。どれも短い作業だが、続きに戻るための足場になる。

昨日の自分が何を考えていたか、完全には思い出せなくてもいい。記録を読めば、次に何を確かめればよいかわかる。その状態を作れたら、今回のメモは十分に役に立っている。
